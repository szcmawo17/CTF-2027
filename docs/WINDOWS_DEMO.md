## Подготовка

В PowerShell из C:\DjangoLearn:

```powershell
.\venv\Scripts\Activate.ps1
python -m pip check
python manage.py check
python manage.py showmigrations competitions
python manage.py makemigrations --check --dry-run
```

Зависимости разработки перечислены в requirements-dev.txt. Не менять ExecutionPolicy всей машины ради активации: можно использовать полный путь venv\Scripts\python.exe.

Перед внедрением 0019: отдельное разрешение, остановка записывающих Django/worker-процессов, свежая SQLite Backup API копия вне Git, проверка читаемости/integrity/FK. Применять только согласованную миграцию, сверять старые данные, PK, связи, container_id и host_port. При ошибке остановиться и сохранить фактическое состояние, без автоматического rollback.

## Ключ

Создать приватный каталог вне репозитория через Проводник. В свойствах → Безопасность → Дополнительно проверить наследование и права: доступ нужен учётной записи оператора Django/worker; исключить ненужные общие группы. Не удалять права системных администраторов без понимания политики машины. Проверить эффективный доступ. POSIX mode 0600 не доказывает защиту Windows ACL.

После подготовки каталога:

```powershell
python manage.py init_checker_key C:\CTF-private\checker.key
$env:CTF_CHECKER_KEY_FILE='C:\CTF-private\checker.key'
```

Путь примерный: каталог должен существовать и быть защищён. Команда не перезаписывает ключ. Не выводить содержимое, не класть ключ в Git или контейнер. Настроить тот же путь в обоих терминалах. Потеря ключа делает старые ciphertext недоступными; просто заменить ключ нельзя. Резервную копию ключа хранить отдельно с ограниченным доступом. Автоматической ротации нет.

## Работа после разрешённого внедрения

Терминал Django:

```powershell
python manage.py runserver 127.0.0.1:8000 --noreload
```

В отдельном терминале с тем же venv и ключом:

```powershell
python manage.py checker_worker --max-jobs 20
```

Команда обрабатывает не более 20 доступных заданий и завершается. Повторять её при появлении заданий и после дедлайна раунда; это не supervisor. В Admin смотреть CheckerJob: pending/running/done/expired, attempts, deadline и безопасные коды результата. Не редактировать задания вручную. После сбоя истёкший lease может быть перехвачен следующим запуском; поздний результат не принимается.

Проверить игровую страницу, таблицу очков и выполнить `python manage.py audit_game_scores --help`, затем аудит выбранного соревнования по указанному синтаксису. Не исправлять историю SQL-запросами.

Для остановки дождаться выхода ограниченного worker, затем Ctrl+C в терминале Django. При аварии worker проверить дочерние процессы через Диспетчер задач; не завершать неизвестные процессы. Остановка Django не останавливает контейнеры. Управление контейнерами здесь не предусмотрено.

## Сценарий демонстрации

1. Показать регистрацию, две команды с разными игроками и фиксированный состав PlayerParticipation.
2. Показать переходы соревнования и права организатора.
3. На разрешённой тестовой инфраструктуре открыть HTTP-раунд; показать pending → running → done и подтверждённый put.
4. Отправить известный тестовый флаг штатным сервисным слоем/формой; показать отказ повторной сдаче.
5. Завершить раунд, обработать get/health, показать итог 21/1 для сценария одного захвата и успешных остальных проверок; сверить audit_game_scores.
6. Объяснить ERROR, retry, дедлайны и отсутствие двойных очков. Не расширять сценарии эксплуатации учебного сервиса.

До проверки Docker показывать отдельно успешный localhost HTTP-тест и подготовленный инфраструктурный код. Не выдавать это за проверенный контейнерный стенд. Следующий этап: разрешённая проверка контейнерного стенда, затем периодический запуск/мониторинг, политика досрочного завершения и изоляция сети.
