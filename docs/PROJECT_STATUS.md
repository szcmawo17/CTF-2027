# PROJECT_STATUS — Attack/Defense CTF Platform

Обновлено: 2026-10-31. Источник: текущая локальная рабочая копия и выполненные проверки.

## Реализовано
- Django config и competitions; модели Competition, Team, Service, TeamService.
- Миграции 0001–0014 применены к рабочей SQLite-базе. Миграции 0010–0012 перенесли старые связи команд и сервисов без изменения PK и данных контейнера; 0013 добавила таблицу приглашений, 0014 — статус регистрации соревнования.
- Django Admin для соревнований/сервисов; Docker SDK, test Flask image.
- Безопасная локальная публикация Docker-портов только на 127.0.0.1; проверка настроек при перезапуске.
- Ручная сверка статуса Docker с базой данных.
- Компенсационный остановочный откат при частичном сбое deploy_competition_services.
- SECRET_KEY читается из .env, не включённого в репозиторий.
- Регистрация, вход, POST-выход, личный кабинет с изменением контактных данных и сменой пароля на стандартной Django User; общий шаблон навигации.
- Публичный список показывает соревнования в статусах регистрации, игры и завершения. Черновики видны пользователям с разрешением `competitions.view_competition`.
- В коде есть TeamMembership с ролями участника и капитана, CompetitionParticipation и уникальные ограничения на членство, капитана, участие и сервис участия. Существующим командам владельцы автоматически не назначаются.
- Зарегистрированный пользователь может создать команду и стать её капитаном. Капитан приглашает существующих пользователей по имени, отзывает приглашения, передаёт роль и исключает участников; адресат принимает или отклоняет приглашение, участник может выйти. Проверки прав находятся в сервисном слое, изменения выполняются POST-запросами.
- Капитан может зарегистрировать свою команду на соревнование только в статусе `registration` и снять её до закрытия регистрации, пока у участия нет TeamService. Регистрация не создаёт контейнеры; развёртывание остаётся действием администратора.
- Всего 61 автоматический тест, включая аккаунты, миграции старых данных, права команд, регистрацию и CSRF.

## Ограничения и технический долг
- Компенсационный откат останавливает контейнеры, но не гарантирует их удаление/восстановление исходной записи БД; возможны orphan-контейнеры при падении до save.
- Нет безопасного автоматического удаления контейнеров и периодической сверки.
- Изоляция сетей/ресурсов для настоящего Attack/Defense не готова; localhost — мера лишь для локального прототипа.
- Обратный переход после создания команд с несколькими участиями невозможен без потери смысла данных; миграция намеренно останавливает такой откат. Резервная копия состояния до миграции сохранена.
- Старые команды пока не имеют капитанов и управляются через Django Admin до ручного назначения пользователя. Приглашения не отправляются по email и не имеют срока действия; для публичного использования нужны лимиты на создание команд и приглашений.
- DEBUG=True, SQLite и захардкоженный ctf-test-service — только для локальной разработки.
- Контактный email в личном кабинете не подтверждается и не используется для входа; самостоятельное восстановление пароля по email не реализовано. Для публичного развёртывания требуются настройки почты, HTTPS и дополнительная защита от перебора паролей.
- Пока не задано правило о членстве одного пользователя в нескольких командах одного соревнования; его нужно определить до игрового процесса. Нет раундов, флагов, чекеров, рейтинга и наблюдаемости.
- Организатор пока меняет статус соревнования через Django Admin; отдельные правила переходов статуса и расписание относятся к следующему этапу.
- Одновременный запуск инфраструктуры и новая регистрация команд требуют отдельной координации перехода статуса; локальный прототип пока не гарантирует безопасную синхронизацию этих операций.
