## Идемпотентность и ограничения

Первоначальная 0016 при повторном вызове функции переноса пыталась повторно вставить игроков и обновляла время фиксации пустого состава. Регрессионные тесты воспроизвели обе ошибки. Исправлена только ещё не применённая 0016; миграции 0001–0014 не менялись.

Теперь точное существующее участие игрока переиспользуется без изменения PK/роли. Противоречивые записи отклоняются до вставки. Уже зафиксированные составы не пересобираются; время фиксации и счётчик блокировки не сбрасываются. Не используется ignore_conflicts, который мог бы скрыть ошибочные данные.

На копии:

- Повторный migrate: No migrations to apply, данные не изменились.
- Прямой повтор seed_rosters: данные всех таблиц не изменились.
- Проверены пять уникальностей: членство, капитан команды, участие команды, игрок соревнования, сервис участия.
- Проверен PROTECT для пользователя, команды, участия и сервиса при наличии связанных записей.
- Несовпадение соревнования игрока и участия отклонено model.full_clean(). Межтабличной проверки этого соответствия непосредственно в SQL нет; обязательны существующие сервисы при записи.
- Все проверки ограничений выполнялись на временных записях внутри откатываемой транзакции. После них копия повторно сверена: записей от проверок не осталось.

На тестовой базе дополнительно проверены повторный перенос непустого состава, сохранение времени фиксации пустого состава, сохранение завершённой истории после изменения членств, отказ при противоречивой частично перенесённой записи и отказ при общем игроке двух старых участий.

## Риски и порядок внедрения

1. Остановить запись приложения на время резервирования и миграций; Docker останавливать для этого не требуется. Нужны отдельное разрешение и проверенная резервная копия перед применением.
2. При появлении старых конфликтующих игроков 0016 намеренно остановится. Транзакция атомарна для каждой миграции отдельно: 0015 к этому моменту уже может быть применена. Не использовать fake и не удалять спорные записи автоматически.
3. Старое running-соревнование с пустыми командами останется таким же; миграция не назначает капитанов и не придумывает игроков. После фиксации состав заблокирован до finished. Дальнейшее решение принимает организатор, завершение само по себе контейнеры не останавливает.
4. Обратная операция 0016 — noop; откат 0015 удалит новые таблицы. Это не безопасный способ восстановить историю. Аварийный возврат требует согласованного восстановления резервной копии и прежней версии кода.
5. Зависший deploying после падения процесса требует отдельной диагностики; автоматического восстановления нет. Реальная надёжность Docker этой репетицией не проверялась.
6. После применения сверить данные и целостность рабочей базы, проверить страницы/Admin. Произвольные SQL/ORM-записи в обход сервисов, PostgreSQL и нагрузочная эксплуатация этой проверкой не покрываются.
