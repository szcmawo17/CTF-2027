## Что реализовано

Существующий mock-режим сохранён. Для HTTP добавлены три модели:

- CheckerEndpoint — доверенная привязка TeamService к UUID экземпляра, ID контейнера, localhost-порту и зашифрованному токену. Создаётся инфраструктурным кодом; редактирования через веб нет.
- CheckerJob — отдельное задание put_flag/get_flag/check_service. Round и TeamService определяются через Flag, без дублирующихся внешних ключей. Хранятся снимок endpoint, дедлайн, UUID lease, число попыток, времена, безопасный код ошибки и результат.
- FlagMaterial — временная зашифрованная доставка исходного флага, связанная с Flag. Сам Flag по-прежнему хранит SHA-256.

Service.runtime выбирает прежний ctf-test-service либо отдельный учебный HTTP-сервис. Значение по умолчанию legacy сохраняет прежнее поведение. В Admin runtime нельзя менять после появления TeamService. Round получил backend http и состояние checking; прежняя история не преобразуется в HTTP-историю.

## Очередь, транзакции и процесс

Разделение: подготовка → claim_job → execute_claim → record_result. Подготовка, захват и фиксация используют существующий CompetitionMutationLock и короткие транзакции. Захват durable: он должен закоммититься до внешнего запроса. execute_claim/run_one явно запрещены внутри atomic. HTTP-модуль не импортирует Django и не работает с БД.

Management command `checker_worker --max-jobs N` обрабатывает максимум N заданий (1–1000, по умолчанию 1) и выходит при пустой доступной очереди. Worker — доверенный локальный процесс оператора с доступом к Django SQLite и отдельному файлу ключа. Это не endpoint для игроков и не система удалённой аутентификации worker.

Состояния задания:

- pending — готово к захвату;
- running — UUID lease и срок до 20 секунд;
- done — окончательный результат OK/DOWN/MUMBLE/ERROR;
- expired — исчерпан дедлайн, результат ERROR.

Максимум три попытки. Истёкший lease можно захватить повторно с новым UUID. Тайм-аут/потеря соединения дают ограниченный повтор того же задания; подтверждённые ответы сервиса не повторяются автоматически. Устаревший, повторный, просроченный результат либо результат для другой конфигурации endpoint не устанавливает флаг и не начисляет очки. Уникальность (flag, operation) защищена БД. SQLite сериализует писателей общей строкой блокировки; select_for_update не считается блокировкой строк SQLite.

Каждая HTTP-операция запускается фиксированным Python-кодом в дочернем процессе spawn. Родитель ждёт результат до 8 секунд; socket timeout — 2 секунды, ответ ограничен 4096 байт, редиректы не выполняются. После результата/тайм-аута дочерний процесс join/terminate, при необходимости kill; если остановка не подтверждена, worker прекращает обработку. Дескрипторы процесса и pipe закрываются. Время запуска процесса и завершения добавляется к HTTP-бюджету.

Это не exactly-once. PUT мог выполниться перед потерей ответа. Повтор использует прежние ID, значение флага и срок. Сервис возвращает успех для идентичной записи и не перезаписывает конфликтующую. UUID lease защищает результат в Django, а не отменяет сетевой пакет.

Жёсткое аварийное завершение родителя ОС не гарантирует остановку его дочернего процесса. multiprocessing daemon обеспечивает очистку при нормальном выходе, но не заменяет Windows Job Object/группу процессов и supervisor. Дочерний процесс не пишет Django-БД; возможный поздний PUT ограничивается неизменяемым ID/значением и сроком на сервисе. Полная эксплуатационная изоляция процессов остаётся задачей.

## Секреты

Используется Fernet из cryptography, без собственной схемы шифрования. Ключ — отдельный файл вне репозитория, путь задаётся через `CTF_CHECKER_KEY_FILE`. Django SECRET_KEY не используется как ключ checker и не передаётся контейнеру.

Команда `init_checker_key` создаёт файл с O_EXCL, не перезаписывает существующий и не печатает ключ. На POSIX запрашивается режим 0600; на Windows оператор обязан ограничить ACL приватного каталога/файла своей учётной записью. Код не утверждает, что POSIX mode автоматически обеспечивает нужный Windows ACL. Рабочий ключ при этой разработке не создавался.

Зашифрованное сообщение содержит назначение (`flag:<id>` или `endpoint:<uuid>`), проверяемое при расшифровке. Worker после перезапуска читает тот же файл ключа. Его потеря/замена блокирует расшифровку; автоматическая ротация и повторное шифрование не реализованы.

FlagMaterial удаляется после окончательного результата put, включая ошибку, либо при истечении срока во время обслуживания очереди. Истёкший материал не расшифровывается. Если worker не запускается, физическое удаление отложено до следующего обслуживания. Токен endpoint хранится зашифрованным весь срок использования экземпляра. SQLite DELETE не означает стирания байтов, а резервные копии могут содержать старый ciphertext: нужны отдельная политика хранения копий и ротация ключа.

Сырые флаги не попадают в обычные игровые таблицы, URL, сообщения Django или вывод команды worker. В память дочернего процесса передаются только данные конкретного запроса. FlagMaterial/CheckerEndpoint не зарегистрированы в Admin; CheckerJob доступен организатору только для чтения, без секретов. Worker имеет доступ к общей БД и ключу по правам ОС, отдельного ограниченного DB-пользователя SQLite нет. Для публичного размещения необходимы DEBUG=False и отключение логирования тел/заголовков секретных запросов внешними компонентами.

## Учебный сервис и доверие

`training_service/app.py` — отдельный Flask-сервис с файловой SQLite. put/get/health требуют отдельный токен экземпляра. Public notes содержит ранее реализованную намеренную ошибку проверки владельца записей; в ревизии уязвимость не изменялась. Команд ОС, загрузки Python-кода, файловых путей пользователя и Docker socket в сервисе нет.

Данные экземпляров разделены. Новый Dockerfile использует UID 10001; подготовленный SDK-вызов задаёт read-only rootfs, cap_drop ALL, no-new-privileges, 128 MB памяти, 0.5 CPU, 64 PID и отдельные tmpfs /tmp и /data. Django-БД и каталоги хоста не монтируются. /data сохраняет записи между HTTP-запросами, но теряет их при остановке контейнера; последующая get-проверка обнаружит потерю. Флаги скрываются от публичных запросов по дедлайну, удаляются из учебного хранилища при следующем запросе после 120 секунд grace.

Используется фиксированный образ `ctf-training-notes:local`; прежний ctf-test-service не менялся. Подготовка токена и фиксация ID/порта отделены от Docker-вызова. Существующий журнал запуска/режим review сохраняется; исчезнувший прежний контейнер учебного сервиса автоматически не пересоздаётся. Сбой после создания контейнера до записи ID по-прежнему может оставить orphan: отдельная инфраструктурная задача.

Worker принимает только порт из доверенной привязки TeamService; host всегда 127.0.0.1, произвольных пользовательских URL/IP/команд нет. Перед секретным запросом выполняется challenge с новым nonce и стандартным HMAC-SHA256 на токене экземпляра. Проверяются UUID и доказательство знания токена. Это защищает от случайной подмены экземпляра/порта; не является TLS и не устраняет MITM/relay на недоверенном хосте. Challenge и рабочий запрос используют отдельные соединения. Локальная сеть и хост считаются доверенными.

Bearer-токен и флаг передаются по локальному HTTP. Оператор Docker может читать окружение контейнера; он входит в доверенную границу. Публикация на 127.0.0.1 не обеспечивает изоляцию A/D; egress контейнеров, сетевые зоны команд, TLS/mTLS и защита хоста пока не реализованы. Этот режим нельзя публиковать как безопасную многопользовательскую инфраструктуру.

## Раунд и политика результатов

При открытии HTTP-раунда создаются флаги issued, пустой put_status и задания установки. Флаг становится installed и доступен для приёма только после актуального put=OK. Остальные результаты оставляют rejected. До подтверждения сдача невозможна.

Ручное завершение допускается только после окончательных put-результатов. Оно переводит Round в checking, закрывает атаки и создаёт get/check задания. При наступлении дедлайна это делает обслуживание очереди. Проверки имеют срок до 60 секунд после начала завершения, но не позже expires_at+60. Если worker возобновился слишком поздно, HTTP уже не выполняется: задания получают expired/ERROR.

Открытие следующего раунда и завершение соревнования запрещены до завершения checking. Итоговые результаты CheckerRun и ScoreEvent фиксируются одной транзакцией после всех обязательных заданий. Установка результата последнего задания также входит в эту транзакцию: ошибка записи очков откатывает весь результат, повтор безопасен.

**Явная политика неопределённости:** после дедлайна/исчерпания попыток ERROR является окончательным неизвестным результатом для данного раунда; он не превращается в DOWN и не даёт соответствующий бонус. Раунд завершается с доступной историей ошибок, а не с утверждением, что все проверки успешны. Attack сохраняется независимо. Defense требует put/get=OK и отсутствия захватов; Availability требует check=OK. Правила +10/+10/+1 и audit_game_scores сохранены.

Автоматическое обслуживание действует только при запущенных проходах worker. Постоянного scheduler/supervisor нет; команда с пустой очередью завершается. Политика досрочного завершения остаётся прежней: организатор может закрыть приём раньше дедлайна после установки флагов. Минимальная длительность, причина и отдельный аудит такого решения остаются в backlog.
