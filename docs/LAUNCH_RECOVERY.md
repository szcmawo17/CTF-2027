# Журнал запуска и безопасная диагностика

Состояние на 2026-11-03, ветка `feature/launch-recovery`: реализация и проверки завершены; **0017 не применена к рабочей базе**. Реальные Docker-операции, commit, push и merge не выполнялись.

## Архитектура

`CompetitionLaunchAttempt` хранит UUID, соревнование, инициатора, начало, окончание, состояние и фиксированное безопасное сообщение. `Competition.current_launch_attempt` указывает на текущую попытку. Одна незавершённая/требующая проверки попытка на соревнование разрешена ограничением БД. CHECK связывает состояние с наличием времени окончания. При удалении организатора ссылка становится NULL, сама история остаётся.

`CompetitionRecoveryAction` хранит явную ручную отметку организатора и безопасный снимок диагностики. UUID диагностики используется как одноразовый идентификатор действия. Журналы в Admin доступны только для чтения; используются существующие active/staff и `competitions.change_competition`, новая система ролей не вводится.

Запуск состоит из трёх отдельных частей:

1. Короткая durable-транзакция с CompetitionMutationLock создаёт попытку, проверяет условия и сохраняет зафиксированный состав вместе с deploying. Durable запрещает оборачивать весь запуск внешней atomic-транзакцией; исключение тестового Django TestCase предусмотрено самим Django.
2. Существующее развёртывание выполняется без удержания транзакции SQLite. Действующий контейнер с сохранённым ID переиспользуется существующим кодом; автоматическое создание/запуск при диагностике отсутствует.
3. Другая короткая транзакция проверяет UUID текущей попытки и её состояние, затем вместе записывает succeeded и running. Старый или повторный результат отклоняется.

Операции Docker и SQLite не атомарны. UUID защищает записи БД, но не отменяет уже отправленный Docker-запрос.

## Политика ошибок

| Ситуация | Состояние и дальнейшее действие |
|---|---|
| Нет прав, недопустимый статус, повторный запуск | Отказ до создания новой попытки и до Docker |
| Не выполнены условия старта | Попытка failed с временем окончания; регистрация остаётся открытой, можно исправить условия и запустить снова |
| Проверка условий/создание попытки не могут записаться из-за недоступности БД | Docker не вызывается; журнал невозможно гарантированно сохранить, если сама БД недоступна |
| Ошибка развёртывания, частичный сбой или ошибка записи успеха | Попытка review и launch_state=review, если удалось записать; состав закрыт, повтор запрещён |
| Аварийный выход или невозможность записать review | Сохраняется ранее закоммиченная in_progress/deploying без подтверждённого окончания |
| Ручная отметка после диагностики | Аудит действия и review; состав и TeamService сохранены, контейнеры не меняются, повтор не разрешается |

Время окончания при перехваченной ошибке означает завершение обработки попытки приложением, а не доказательство отсутствия незавершённой операции в Docker. При ручной отметке выполняющегося запуска время окончания не придумывается. Старые running/finished и deploying/failed без журнала не получают фиктивных исторических попыток при миграции.

Прежняя политика повторного запуска после произвольного Docker-сбоя ужесточена намеренно: тайм-аут SDK может означать, что контейнер создан, но его ID не сохранён. Автоматический повтор способен создать второй контейнер. Без достоверного завершения процесса и сверки ресурсов разблокировка не реализована.

## Диагностика и Admin

В карточке и списке соревнований доступна ссылка «История и диагностика». GET показывает только БД и историю. POST «Проверить БД и Docker без изменений» получает короткий снимок БД, затем вызывает только получение известных контейнеров, закрывает клиент и повторно сверяет снимок БД. Длительной транзакции вокруг Docker нет.

Отчёт содержит ID команд, игроков и ролей из зафиксированного состава, TeamService, статусы БД/Docker, проверку localhost-порта и отсутствующие/лишние пары участия и сервиса. NotFound, недоступный Docker и неизвестное состояние показаны явно. Диагностика не вызывает `sync_team_service_status`, не сохраняет изменения статуса, не читает логи/env и не сохраняет полные Docker attrs или текст исключений. Проверка localhost не гарантирует Attack/Defense-изоляцию.

Явное действие «Зафиксировать ручное вмешательство» допустимо только для незавершённого запуска. Подписанный результат диагностики действует 5 минут, привязан к организатору, соревнованию и отпечатку состояния БД. Если БД менялась во время/после проверки, подпись неверна, срок вышел или действие повторено — операция отклоняется. Срок подписи ограничивает свежесть отчёта, **не подтверждает остановку процесса**.

Ручная отметка может быть поставлена и во время работы исходного worker. Его последующая запись успеха будет отклонена, однако сам worker физически не остановлен. Поэтому никакого reset, unlock или автоматического retry в этом интерфейсе нет. Отдельные старые stop/restart-действия Admin запрещены при уже установленном deploying/failed/review; это не полная координация всех внешних операций.

Необходимо отдельно спроектировать управляемый worker, достоверную остановку, fencing Docker-операций и поиск orphan-контейнеров. До этого диагностика и ручная отметка — максимально безопасный доступный сценарий. Задачи зафиксированы в [POLISH_BACKLOG.md](POLISH_BACKLOG.md).
